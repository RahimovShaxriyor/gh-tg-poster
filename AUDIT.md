## 3. Подробности по критичным и высоким

### К1. Перегенерация, завершившаяся после публикации, приводит к дублю в канале

**Где:** `lib/poster.js` `generate()`. Статус проверяется один раз в начале (строки 51-56). После `await ctx.ai(...)` все `update` безусловные:
- строка 66: `set status='skipped'`;
- строка 72: `set status='failed'`;
- строка 77: `set text=?, status='failed'`;
- строка 85: `set text=?, status='draft'`;
- строка 116: в catch `set status='failed'`.

**Воспроизведение [запуск]:** скрипт с реальными `generate()` и `publish()`, ИИ отвечает с задержкой.
1. Черновик → `generate(id, true)` (кнопка «Другой вариант»), ИИ ещё думает.
2. `publish(id)` (кнопка «Опубликовать» в панели остаётся активной, `withButton` блокирует только саму кнопку перегенерации; или кнопка в Telegram).
3. ИИ отвечает → пост снова `draft` с новым текстом, `tg_message_id` остаётся от первой отправки.
4. `publish(id)` проходит второй раз.

Итог: `после publish=sent, после ответа ИИ=draft, повторная публикация: да, сообщений в канале: 2`. При ошибке ИИ в том же окне отправленный пост становится `failed`, и кнопка «Повторить» отправит его ещё раз.

**Последствия:** дубль в канале; история в панели врёт (отправленный пост выглядит черновиком).

**Исправление:** захватывать пост атомарно и обновлять только при ожидаемом статусе.
```js
// в начале generate(): атомарный захват
const lock = ctx.db.prepare(
  "update posts set status='generating' where id=? and status in ('draft','failed','skipped','rejected')"
).run(id);
if (!lock.changes) throw new Error("Пост сейчас обрабатывается или уже отправлен");
// все дальнейшие update — только из generating:
ctx.db.prepare("update posts set text=?, status='draft', error=null where id=? and status='generating'").run(trimmed, id);
```
Плюс: `publish()` принимает только `draft` и `failed` (уже так); `recoverStuckSending()` переводит `generating` в `failed` при старте; в UI на время перегенерации блокировать «Опубликовать» и «Отклонить» у этой карточки; добавить бейдж «Генерируется…». Тест: сценарий выше.

### В1. «SKIP.» публикуется в канал

**Где:** `lib/poster.js:65` `if (text === "SKIP")`.

**Воспроизведение [запуск]:** режим auto, debounce 0, ИИ отвечает:
- `"SKIP."` → в канал ушло `["SKIP."]`;
- `"**SKIP**"` → в канал ушло `["**SKIP**"]`;
- `"skip"` → в канал ушло `["skip"]`.

Модели нередко добавляют точку или разметку.

**Исправление:**
```js
const isSkip = (t) => /^[\s*_`"'«».!]*skip[\s*_`"'«».!]*$/i.test(t || "");
if (isSkip(text)) { ... }
```
Дополнительно в auto-режиме не публиковать текст короче, например, 20 символов: оставлять его черновиком.

### В2. Force-push или rebase: пост по 30 старым коммитам

**Где:** `lib/poster.js:241-244`. Если `idx === -1`, в `fresh` попадают все `commits`. То же для дайджеста, строки 204-205.

**Воспроизведение [запуск]:** запомнен `old0`, затем история переписана (верхний коммит заменён). В черновик попало `30 коммитов`. В auto они уходят в канал. Тот же путь срабатывает, когда за один интервал пришло больше 30 коммитов: это нормально, но и тогда лучше пометить черновик.

**Последствия:** анонс «новостей», которые уже публиковались. В auto это сразу в канале.

**Исправление:** при `idx === -1` вызвать `GET /repos/{repo}/compare/{last}...{head}`:
- `status === "ahead"`: брать `commits` из ответа compare;
- `diverged`, `behind` или 404 (старый коммит пропал): создать черновик с пометкой «история переписана», **никогда не публиковать автоматически**, взять только `ahead_by` верхних коммитов или просто сдвинуть `last_sha` и записать предупреждение в `last_error`.

Удаление ветки: GitHub вернёт 404, в `last_error` будет «доступ отозван», что неточно. Нужно отдельное сообщение «ветка не найдена».

### В3. Бэкап «успешен», но пустой

**Где:** `scripts/backup.sh:22-26`, ветка `cp`.

**Воспроизведение [запуск]:** копия скрипта во временной папке, база в WAL с 50 строками, ещё не сброшенными в основной файл, `sqlite3` убран из PATH. Вывод: `Резервная копия успешно создана`; проверка копии: `no such table: posts`; права копии `644`. На стандартном Ubuntu-сервере утилиты `sqlite3` по умолчанию нет.

Ещё одна проблема [гипотеза]: база в `./data` создаётся root-ом внутри контейнера. Запуск `sqlite3 .backup` от обычного пользователя может упасть на доступе к `-shm`, и `set -e` прервёт скрипт.

**Исправление:** делать бэкап изнутри контейнера средствами приложения, где better-sqlite3 уже есть:
```sh
docker compose exec -T app node -e "require('better-sqlite3')('data/app.db').backup('data/backup-tmp.db').then(()=>process.exit(0))"
mv data/backup-tmp.db "backups/app_${TIMESTAMP}.db"; chmod 600 "backups/app_${TIMESTAMP}.db"
```
либо `VACUUM INTO`. Ветку с `cp` убрать совсем: лучше упасть, чем выдать пустую копию. После копии проверять `PRAGMA integrity_check` и наличие таблицы `posts`. Добавить `umask 077`.

### В4. Правки черновика теряются при автообновлении

**Где:** `public/app.js:420-457` `renderFeed()` сохраняет DOM только у textarea **в фокусе**; `setInterval(loadState, 30000)` на строке 1407.

**Воспроизведение [запуск]:** в браузере ввёл «МОЯ ПРАВКА» в первый черновик, кликнул вне поля, вызвал тот же `loadState()`. Результат: `ПОТЕРЯНА (стало: Пост №56 …)`.

**Последствия:** пользователь правит текст, отвлекается, а через 30 секунд текст молча откатывается к варианту ИИ. Если затем нажать «Опубликовать», уйдёт неправленый текст.

**Исправление:** хранить черновики в `state.drafts[id]` (на событие `input`) и при пересоздании карточки подставлять сохранённое значение. Ещё лучше добавить серверное сохранение (`POST /api/posts/:id/text` с debounce) и индикатор «есть несохранённые правки». Дополнительно приостанавливать автообновление, пока есть несохранённые правки.

## 4. Что работает хорошо

- **Тесты:** 62 теста, 3 прогона подряд зелёные, около 7,5 с каждый [запуск]. Тесты используют настоящие модули и подменяют только `fetch` на границе сети; это проверка поведения, а не моков.
- **Двойной клик «Опубликовать»** защищён атомарным `update … where status in ('draft','failed')` (lib/poster.js:19-23) [запуск в тестах].
- **Зависшие `sending`** при старте переводятся в `failed` + `interrupted`, в UI показывается предупреждение (lib/db.js:186-193) [код + тест].
- **Пароль:** scrypt с солью, сравнение за постоянное время, перехеширование старого sha256 [код + тест]. Смена пароля отзывает все сессии: старая cookie после смены получила 401 [запуск].
- **Ограничение попыток входа:** 6-я попытка получает 429, блок на 10 минут [запуск]. `trust proxy` настроен на `loopback, uniquelocal`, Express берёт крайний правый недоверенный IP. Подмена левой части XFF блок не обходит [тест]. Подмена с loopback работает, но в проде к приложению ходит только Caddy, порт 3000 наружу не открыт [запуск + код].
- **Белый список настроек:** `last_sha`, `tg_owner_chat_id`, `admin_password_hash` через `/api/settings` не меняются [запуск + тест]. Значения валидируются, неверные отклоняются целиком.
- **Шифрование секретов:** AES-256-GCM с проверкой целостности [код]. При смене ключа сервер не падает, `/api/state` показывает «секреты не удалось расшифровать» [запуск + тест]. Секреты не возвращаются в API.
- **XSS:** весь вывод через `textContent` и DOM API, `innerHTML` нет [код]. `<img onerror>` в тексте поста и в сообщении коммита отобразился как текст [запуск]. CSP без `unsafe-inline` для скриптов, `X-Frame-Options: DENY`, `nosniff` [запуск].
- **SQL:** только параметризованные запросы. Фильтр из query string передаётся параметром [код].
- **Кнопки бота:** чужой `from.id` отклоняется. Канал привязывается автоматически только если бота добавил владелец. Код привязки одноразовый, хранится как хеш, живёт 15 минут [код + тест].
- **Таймауты** есть на всех внешних запросах: GitHub 20 с, Telegram 40 с, ИИ 120 с [код + тест].
- **Первый запуск** не постит старые коммиты [код + тест]. Смена репозитория или ветки сбрасывает `last_sha` [код].
- **Дайджест и часовые пояса:** время считается через `Intl` с IANA-зоной, поэтому переход на летнее время обрабатывается правильно. Сравнение `>=` переживает пропущенный час и простой сервера [код].
- **Вёрстка на 1920 px** в светлой и тёмной теме аккуратная. Тёмная тема работает через `prefers-color-scheme` [запуск, скриншоты].
- **Зависимости:** `npm audit` нашёл 0 уязвимостей [запуск].
- **Утечки:** в логах сервера за сессию только «Готово: порт» [запуск]. Ошибки проходят через `cleanError` (кроме Н7).
- **Таймеры и память:** `schedulePoll` очищает старый интервал; карта попыток входа чистится; кэш токенов GitHub ограничен одной установкой [код].

## 5. Чего не хватает

### Необходимо до первого запуска
1. Исправить К1, В1, В2, В4 (или явно не включать auto и не перегенерировать без перезагрузки страницы).
2. Рабочий бэкап (В3) и проверенное восстановление из него.
3. Уведомление владельцу в Telegram о сбоях: пост упал, GitHub отозван, ИИ без баланса, бот удалён из канала. Сейчас об этом можно узнать, только открыв панель.
4. Процедура восстановления забытого пароля (С12), например `docker compose exec app node scripts/reset-password.js`, и описание её в README.
5. Корректная остановка (SIGTERM) и запуск контейнера не от root (С9, С11, С13).

### Желательно
- Журнал событий: проверки, ошибки, публикации, смены настроек; хотя бы последние 200 записей в таблице `events`.
- Ретраи с учётом `retry_after` для Telegram и экспоненциальная пауза для ИИ (С8); автоповтор `failed` в auto-режиме 1–2 раза.
- Серверное сохранение правок черновика (В4).
- Показ исходных коммитов у поста (С5): хранить `input` структурировано или отдельно `commits_json`.
- Восстановление отклонённых постов и фильтр «Отклонённые» (Н3).
- Редактирование уже отправленного поста через `editMessageText`.
- Предпросмотр с форматированием Telegram и выбор `parse_mode`.
- Внешний мониторинг: `/health` сейчас всегда `ok`, даже если GitHub-проверки падают час. Стоит добавить `last_success_at` и отдавать 503, если проверок не было дольше N интервалов.
- Настройка HSTS и `-X-Powered-By` в Caddyfile.

### Можно позже
- Шаблоны постов (подпись, хэштеги, ссылка на коммит или релиз).
- Экспорт истории (CSV/JSON).
- Несколько репозиториев и каналов.
- Очистка старых `input` (сейчас до ~30 КБ на пост; на сотне постов в месяц это около 3 МБ, некритично).
- Проверка новых версий и `docker compose pull` по инструкции.
- Webhook GitHub вместо опроса (быстрее и экономнее лимитов).
- Фронтенд-тесты (Playwright) на основные сценарии.

## 6. Что не удалось проверить и ручной чеклист

**Не проверено и почему:**
- Реальные GitHub, Telegram, Anthropic и OpenAI: ключей нет, внешние вызовы заменялись заглушкой.
- Caddy и HTTPS: связку Caddy → app с реальным доменом не поднимал. Поведение Caddy с `X-Forwarded-For` описано по документации: по умолчанию он не доверяет входящему XFF и подставляет адрес клиента. Это не проверено запуском.
- Сборка на x86_64: проверял только linux/arm64 (Mac M-серии); результат на обычном x64-сервере может отличаться (см. раздел 8).
- Поведение Telegram при 429 и удалении бота из канала проверено только по коду.
- Права доступа к файлам внутри реального тома Docker на Linux.
- Контраст по WCAG инструментально не измерялся, только визуально по скриншотам.

**Ручной чеклист с реальными ключами (на сервере):**
1. `docker compose up -d --build`, затем `docker compose ps`: app в состоянии `healthy`. Открыть `https://ДОМЕН`, замок в браузере на месте.
2. С телефона 6 раз ввести неверный пароль: 6-я попытка даёт «Слишком много попыток». С компьютера вход при этом работает (проверка реального IP через Caddy).
3. Сохранить fine-grained токен GitHub (Contents: Read-only, один репозиторий) → «Проверить подключение».
4. Токен бота → «Получить код» → `/start код` боту в личку → бот отвечает «Вы привязаны».
5. Добавить бота админом в канал **с вашего аккаунта**: канал подставится сам. Нажать «Отправить тест» и увидеть сообщение в канале.
6. Ключ и модель ИИ → «Проверить».
7. Режим approve, debounce 1 мин. Сделать коммит → через 1–6 минут появится черновик → отредактировать, **не уходить с поля** → «Опубликовать» → пост в канале, ссылка «Открыть в канале» работает.
8. Включить «Присылать черновики в личку» → новый коммит → в личке кнопки → «Опубликовать» → один пост в канале.
9. Нажать «Другой вариант» и **ничего не нажимать**, пока не обновится. До исправления К1 этот шаг опасен.
10. Удалить бота из канала → коммит → пост `failed` с понятной ошибкой. Вернуть бота → «Повторить».
11. Запустить `scripts/backup.sh` на сервере и открыть копию: `sqlite3 backups/app_*.db "select count(*) from posts"`. Число должно совпасть с панелью.
12. `docker compose restart app`: время рестарта (около 10 с означает, что SIGTERM не обработан), посты не потерялись.
13. `ls -l data/` на сервере: владелец и права файлов базы.

1. Первый `npm install --omit=dev` упал: install-скрипт better-sqlite3 (`node-gyp rebuild`) не нашёл python3 (`gyp ERR! find Python`).
